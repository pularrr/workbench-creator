# v2.0 — 可插拔文本处理工作台架构

> 状态：**开发计划已写入，暂不开发**。本文档描述 v2.0 的目标、架构、迁移路径和验收标准，待 v1.2.x 稳定后启动。

## 1. 目标

将论文工作台（`dsh-thesis-agent`）的核心架构抽象为**可插拔的文本处理工作台框架**，使相同的"双区编辑 + 状态治理 + 模板驱动 + 多模态凭证 + RAG 检索"架构能够快速迁移到其他有固定流程的文本生成任务。

### 1.1 核心思想

论文工作台的本质是一个**"文本生成框架 + 文本生成逻辑 + 文本内容凭证"**的三元组合：

| 层 | 论文场景 | 抽象含义 |
|---|---|---|
| 文本生成框架 | 大纲（outline）+ 章节结构 | "写什么"——文本的骨架和分区 |
| 文本生成逻辑 | 行文逻辑（logicBlocks）+ 承接关系 | "怎么写"——每段的写作目标、过渡、论证链 |
| 文本内容凭证 | 引用（citations）+ 来源绑定（sourceBindings）+ 文献（literature） | "凭什么写"——每句话的证据来源和可追溯性 |

v2.0 将这三层**插件化**，由 LLM 根据用户描述的文本任务类型，自主确定每一层应该使用哪些插件。

### 1.2 目标场景

用户通过自然语言描述目标任务，例如：

- "基于论文工作台的架构，帮我生成一个面向**专利撰写**的工作台"
- "帮我做一个**法律合同审查**的工作台"
- "生成一个**技术方案文档**写作工作台"
- "做一个**临床试验报告**工作台"

系统自动：
1. 识别文本任务类型
2. 选择/生成对应的"文本生成框架"插件（大纲结构）
3. 选择/生成对应的"文本生成逻辑"插件（写作逻辑）
4. 选择/生成对应的"文本内容凭证"插件（证据/引用机制）
5. 生成本地 DSH 插件 + 3199 工作台 UI
6. 指导用户安装

### 2.1 整体架构

```
┌─────────────────────────────────────────────────────────┐

└──────────────────────┬──────────────────────────────────┘
                       │ 安装/加载
┌──────────────────────▼──────────────────────────────────┐
│              可插拔工作台框架（Workbench Core）              │
│  ┌────────────┐  ┌────────────┐  ┌──────────────────┐  │
│  │ 框架插件    │  │ 逻辑插件    │  │ 凭证插件           │  │
│  │ Framework  │  │ Logic      │  │ Evidence          │  │
│  │ (大纲/结构) │  │ (写作逻辑)  │  │ (引用/来源/证据)   │  │
│  └─────┬──────┘  └─────┬──────┘  └────────┬─────────┘  │
│        │               │                    │            │

└──────────────────────────────────────────────────────────┘
```

### 2.2 三层插件契约

#### 2.2.1 框架插件（Framework Plugin）

**职责**：定义文本的骨架结构——有哪些章节、每章的目标、预计字数、预计图表。

**契约接口**：
```js
{
  id: 'patent-framework',
  name: '专利撰写框架',
  taskType: 'patent',
  generateOutline(input) {
    // 返回 outline 节点数组
    // 每个节点: { id, title, objective, targetWords, expectedFigures, expectedTables, expectedMedia }
  },
  validateOutline(outline) {
    // 校验大纲是否符合该任务类型的规范
    // 返回 { valid, issues[] }
  }
}
```

**内置框架插件示例**：
- `thesis-framework`：学位论文（摘要/绪论/相关工作/方法/实验/结论/参考文献）
- `patent-framework`：专利（技术领域/背景技术/发明内容/附图说明/具体实施方式/权利要求）
- `contract-framework`：法律合同（当事人/鉴于条款/定义/权利义务/违约责任/争议解决/附则）
- `tech-report-framework`：技术报告（概述/需求/方案/实现/测试/结论）

#### 2.2.2 逻辑插件（Logic Plugin）

**职责**：定义每个文本块的写作逻辑——写作目标、承接关系、论证链、语气风格。

**契约接口**：
```js
{
  id: 'patent-logic',
  name: '专利写作逻辑',
  taskType: 'patent',
  generateLogic(outlineNode, context) {
    // 返回 logicBlock 数组
    // 每个块: { id, outlineNodeId, purpose, transition, targetWords, style }
  },
  suggestRewrite(block, feedback) {
    // 根据反馈建议重写方向
  }
}
```

**逻辑维度**（可配置）：
- 论文：学术严谨性、文献引用密度、论证链完整性
- 专利：权利要求保护范围、技术效果描述、实施例充分性
- 合同：条款完备性、风险分配、法律术语准确性
- 技术报告：技术深度、可复现性、数据支撑

#### 2.2.3 凭证插件（Evidence Plugin）

**职责**：定义文本内容的证据机制——引用格式、来源绑定、证据评估、可信度分级。

**契约接口**：
```js
{
  id: 'patent-evidence',
  name: '专利凭证机制',
  taskType: 'patent',
  formatCitation(source, style) {
    // 格式化引用
  },
  evaluateEvidence(block, bindings) {
    // 评估证据充分性
    // 返回 { sufficient, missingEvidence[], confidence }
  },
  citationStyle: 'gb-t-7714' | 'ieee' | 'apa' | 'patent-citation' | 'legal-citation' | 'custom'
}
```

**凭证类型**：
- 论文：学术文献引用（GB/T 7714 / IEEE / APA）
- 专利：现有技术引用、对比文件、法律状态
- 合同：法律法规引用、判例引用、行业标准
- 技术报告：测试数据引用、标准规范引用、专利引用

### 2.3 工作台运行时（Workbench Runtime）

从论文工作台中抽象出的通用运行时，与具体任务类型解耦：

| 组件 | 论文工作台现状 | v2.0 抽象 |
|---|---|---|
| 双区编辑 | 4:3 可拖拽 | 保持不变，作为标准布局 |
| AgentRun 状态机 | 13 状态固定 | 可配置状态集，由框架插件定义 |
| 模板引擎 | 3 套内置论文模板 | 通用模板引擎，支持文本/格式模板 |
| RAG 检索 | embedding + rerank | 保持不变，凭证插件定义检索策略 |
| 多模态管理 | PDF/Word/图片/公式 | 保持不变，框架插件定义需要哪些模态 |
| 导出引擎 | DOCX/LaTeX/PDF | 可扩展导出器，由格式模板定义 |
| 重新生成 | regenerationRequests 队列 | 保持不变，逻辑插件定义重生成策略 |

### 2.4 LLM 自主插件选择

当用户描述新任务时，LLM 按以下流程确定插件组合：

```
用户描述任务
  ↓
LLM 识别 taskType（专利/合同/报告/...）
  ↓
检索内置插件注册表（plugin-registry.json）
  ├─ 匹配到框架插件 → 使用
  ├─ 未匹配 → LLM 生成新框架插件（基于任务描述 + 通用模板）
  ↓
同理选择/生成逻辑插件、凭证插件
  ↓
生成工作台插件包（含 plugin.json + 三层插件 + 模板）
  ↓
写入本地目录 + 指导用户安装
```

**插件注册表**（`plugin-registry.json`）：
```json
{
  "frameworks": [
    { "id": "thesis-framework", "taskType": "thesis", "name": "学位论文", "description": "..." },
    { "id": "patent-framework", "taskType": "patent", "name": "专利撰写", "description": "..." }
  ],
  "logics": [...],
  "evidences": [...]
}
```

## 3. 迁移路径

### 3.1 从论文工作台到可插拔框架

```
v1.x（论文工作台）
  │
  ├─ 抽象出 Workbench Runtime（与论文解耦）
  ├─ 抽象出 Framework/Logic/Evidence 三层插件契约
  ├─ 将论文-specific 逻辑封装为 thesis-* 插件
  │
  ▼
v2.0（可插拔工作台框架）
  │
  ├─ 内置 thesis/patent/contract/tech-report 四套插件
  ├─ LLM 可生成新任务类型的插件
  └─ 用户安装后获得对应工作台
```

## 4. 验收标准

### 4.1 功能验收

- [ ] 用户说"基于论文工作台架构，生成一个专利撰写工作台"，系统能生成完整的本地插件包
- [ ] 生成的插件包含 framework/logic/evidence 三层插件，且每层都有合理的默认实现
- [ ] 用户按指导安装后，能在 DSH 中加载该工作台，3199 端口显示对应 UI
- [ ] 工作台保留双区 4:3 可拖拽布局、高交互编辑/保存、重新生成按钮
- [ ] 工作台的大纲/逻辑/引用面板显示对应任务类型的内容（而非论文内容）
- [ ] 模板 tab 显示该任务类型的预设模板，用户可二次编辑保存
- [ ] 导出功能支持该任务类型的格式（如专利导出为 DOCX + 权利要求书格式）

### 4.2 架构验收

- [ ] Workbench Runtime 与具体任务类型完全解耦，不包含论文-specific 逻辑
- [ ] 三层插件契约清晰，新增任务类型只需实现三个插件 + 模板
- [ ] LLM 生成的插件能通过插件加载器正常加载，无需修改框架代码
- [ ] 论文工作台（v1.x 的功能）能作为 thesis 插件在 v2.0 框架下正常运行

### 4.3 质量验收

- [ ] 全量测试通过（≥ v1.2.0 的测试数 + 新增插件测试）
- [ ] `npm run check` 通过
- [ ] 页面 JS 语法验证通过（`verify-page-js.cjs`）
- [ ] 至少 2 个非论文任务类型的端到端验证（专利 + 合同/技术报告）

## 6. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| LLM 生成的插件质量不稳定 | 生成的工作台可能无法正常运行 | 提供插件模板骨架，LLM 只填充差异部分；生成后自动运行语法检查和基础测试 |
| 三层插件契约设计不合理 | 后续新增任务类型时需要修改契约 | 先在论文+专利两个差异较大的场景上验证契约，再固化 |
| Workbench Runtime 抽象过度 | 通用运行时变得复杂，论文场景反而不好用 | 保持论文场景作为一等公民，抽象时不牺牲论文体验 |
| DSH 插件加载机制限制 | 生成的插件可能无法被 DSH 正常加载 | 先验证 DSH 插件的动态加载能力，必要时改为"生成代码 + 用户手动 link" |

## 7. 与 v1.x 的兼容性

- v1.x 的论文工作台功能在 v2.0 中作为 `thesis-*` 插件保留，功能不降级
- v1.x 的状态文件（`state.json`）在 v2.0 中可通过迁移脚本导入
- v1.x 的导出格式（DOCX/LaTeX/PDF）在 v2.0 中作为默认导出器保留
- 用户已有的论文项目在 v2.0 中可正常打开和编辑
