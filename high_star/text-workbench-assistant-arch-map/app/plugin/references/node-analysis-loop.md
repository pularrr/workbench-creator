# 统一逐节点分析循环

宿主 LLM 的完整网络扩展与应用内 `collectAdaptiveResearch` 使用同一语义状态机。执行环境不同，但节点分析顺序、缺口定义和完成标准相同。

## 1. 基线分析 baseline

节点第一次出队时，先不使用栏目缺失列表，也不以搜索命中的若干资料作为答案框架。把当前节点作为完整知识对象，自主分析：对象与目的、内部机制、组成和依赖、输入输出、真实实现或使用过程、工程约束、意义、失效和验证。随后才把实质结论归入理论知识、应用知识或其他知识栏目。

基线阶段优先分析当前节点并写卡片；确有必要时可以同时提出相关候选节点，但候选数量不能替代当前节点的分析深度。它的目的不是填满所有栏目，而是避免栏目清单和已有短摘要过早限制模型对节点的理解。

## 2. 结构分析 skeleton

当前节点确实存在可独立学习的下级对象时，先规划 domain/category 导航骨架，再放置 entity。结构分析不得清除基线阶段的卡片，也不得为了增加节点数量把同一实现过程拆成无意义碎片。

## 3. 缺口深挖 gap

结合基线成果、正式卡片、邻域与待审查批次，列出具体且可回答的未解决问题。围绕每个缺口继续回答当前节点，适用时覆盖：

- 它是什么以及关键边界；
- 为什么成立，或内部如何实现；
- 输入输出、关键步骤及依赖；
- 这样设计的意义和工程取舍；
- 失败条件、可观察症状与验证方法。

“找到三条资料”“生成两个节点”或“已经写过 definition”不表示缺口解决。回答应形成机制链或实现链，再归档到卡片。多个缺口可以拆成子调用，但每个子调用必须完整解决被分配的问题，而不是各自产生若干关键词。

## 4. 去重、检查点与停止

新内容与正式卡片和当前任务批次比较：语义相同则不重复；新内容更完整时补充或替换原栏目。检查点保存每个 topic 当前仍开放的缺口，而不是历史上出现过的所有缺口并集。只有适用缺口得到有机制、有实现细节且可检查的回答，并连续复查无实质新增，才可报告收敛。预算耗尽、调用失败和待核验来源分别记录，均不得改写成完成。

应用运行时的可执行规则位于 `core/agent/node-analysis-policy.ts`；本文是宿主 LLM 必须遵循的同构规则。
