# 完整开发提示词

输入：已确认 {{profile_json}} 与 {{mvp_network}}、主题 {{topic}}、来源 {{references}}。调用完整生成前必须同时持有与 `profileId + mvp_network` 匹配的 `mvpAcceptanceToken`；没有令牌就停止并请求用户验收 MVP。

在原网络上继续研究，保留确认过的根、域和节点身份。逐节点严格执行 `references/node-analysis-loop.md` 的同构三阶段：baseline 先对节点进行不受栏目缺口限制的整体分析并归档卡片；skeleton 再规划必要导航结构；gap 最后围绕尚未解决的具体问题给出机制、实现、意义、失效和验证等适用内容。每个节点作为新的局部根时，独立重置轮次、局部观察、开放缺口、静默计数和局部新增节点预算；新增节点进入待访问队列，之后也获得同样完整的扩展能力。多个缺口可分批处理，但每个缺口必须完整回答，统一合并时去除语义重复并解析临时 ID 和跨批父级。

每批先把候选放入无卡片的层级骨架：优先复用或建立 category 中间类别，再生成具体节点。逐父节点统计直接子节点；超过 maxPrimaryChildren（默认8）时先按单一稳定维度重组。不得使用从总根累计的 maxDepth 截断；主要域至少选择一条代表路径继续追问到语义不可再分，通常不少于6层。结构通过后才扩写卡片。

80–150节点为参考目标，不设输出上限。构建由宿主 LLM 分批完成，禁止调用项目已配置的 DeepSeek/其他 Provider。每批保存到项目外隔离任务目录，达到宿主预算时保留成果并列出剩余缺口，不能声称收敛。

完整读取 `references/knowledge-card-semantics.md` 后选择栏目。理论知识必须区分定义、原理、成立假设和理论公式；应用知识必须围绕任务场景、输入输出、落地流程、工程取舍、失效模式和验证方法展开。按节点类型满足最低语义覆盖，但不机械填满13栏目。具体指标和论文结论必须有可核验来源；未经核验标注。problem 与方法分离，通过 MITIGATES 联系。

`code` 栏目的代码正文必须写入 block.code，并设置 block.text 为简短说明或空字符串、block.language 为支持的语言标识；不得把代码只写进 text。普通栏目正文写入 text。

输出与 MVP 相同的 KnowledgeNetwork 契约；保留证据，不仅输出节点列表。随后统一校验与语义审查，再创建脚手架和注入数据。
