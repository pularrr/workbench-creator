# 先总后分的层级构造法

先构造导航骨架，再填写细节。不要一边想到概念一边直接挂到知识域下。

先读取 Profile 的 `hierarchy`。仅在它启用且中间节点类型包含 `category` 时，使用以下类别流程；代码图或流程图应使用 Profile 声明的 repository/package/file/symbol、阶段或组件层级，不插入无意义的 category。

1. 写出根节点和语义域，只回答“这张图按哪些稳定维度组织”。
2. 对每个域先列 2–8 个中间类别。类别应有可命名的共同边界，例如概念族、阶段、机制、子系统、输入输出角色或问题类型；使用 `category`。不要创建“其他”“综合知识”等空分类。
3. 再把具体的 concept、method、algorithm、problem、component 等叶子放入类别。一个节点只表达一个知识实体，但“单一”不等于“直接挂在域下”。
4. 对每个父节点做宽度审查。6–8 个直接子节点时规划分类；超过 Profile 的上限（默认8）时重新聚类为 2–8 个有意义的类别，并递归审查新类别。不能为了过校验机械分成“第一组/第二组”。
5. 对同层节点做抽象级别审查。父子之间应能自然读成“B 属于 A / B 是 A 的一种 / B 是 A 的组成或阶段”。同一父节点的孩子应使用同一个划分维度，抽象级别相近。
6. 对深度做语义审查，而不是用固定层数截断。从根到叶应能形成连续可解释的知识链。完整网络至少选择各主要域的一条代表路径继续追问，直到再拆分只会产生步骤细节、实例数据或重复结论；通常应出现不少于6层的代表路径。
7. 每个新节点作为父节点被访问时，都视为新的局部根并重新获得完整 ReAct 轮次、局部观察、静默计数和局部新增节点预算。全局时间、调用和访问主题预算只决定何时保留检查点，不得被解释为该节点或网络已经收敛。

判断两个高度相关节点时依次提问：

1. 一个是否包含、概括、组成、前置或产出另一个？是则优先表达为主树父子关系，或使用有方向的类型边。
2. 二者是否共享一个当前缺失且有真实含义的上位类别？是则创建或复用该类别，再让二者成为同级。
3. 只有二者处于相同抽象级别、互不包含且确实可比较时，才使用同级和 `SIMILAR_TO` / `ALTERNATIVE_TO`。

完成骨架后再生成知识卡。`categoryPlan` 中的重挂载提示必须由 Build 应用为真实父级变更。审查时输出每个父节点的直接子节点数、使用的划分维度、主要域代表路径深度，以及所有过宽、过浅和因全局预算尚未展开的节点。
