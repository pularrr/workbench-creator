# 文本工作台完整改造需求与验收清单

## 一、项目目标

将当前“工作台页面、DSH 对话、Core 服务、SQLite 数据存储”改造成一个真正可协同、可追踪、可验收的本地写作工作系统：

- 用户在工作台点击功能键后，DSH 能明确知道请求来自哪个项目和哪个对话；
- 用户可以看到请求、执行过程、结果和确认动作；
- AI 不能静默覆盖正文、大纲或行文逻辑；
- 文献检索结果要可解释、可筛选、可追溯；
- 项目、材料、任务和版本在重启后仍能恢复；
- 所有关键操作都有明确反馈和可审计记录。

## 二、必须解决的问题

### 1. 工作台与 DSH 对话割裂

当前问题：

- 页面功能键创建任务后，用户不知道是否发送成功；
- DSH 对话中看不到页面请求、执行进度和返回结果；
- 任务长期停留在 `queued`，用户不知道谁负责领取；
- 页面和 DSH 之间缺少统一的协作时间线。

要求：

- 页面操作必须生成可见的请求卡片；
- 请求必须关联 `sessionId`、`assistantKey`、`workspaceId`、`projectId`；
- DSH 能读取、领取、更新、完成和失败任务；
- 页面显示任务生命周期和具体原因；
- DSH 对话能够显示页面请求和执行结果；
- 若 DSH 宿主不支持消息注入，必须明确显示“已写入协作事件，但未注入聊天消息”，不能假装已经发到对话。

### 2. 常驻执行器缺失

当前 Core 只能排队，不能自动领取 AI 任务。

要求：

- 提供可启动、可停止、可查看状态的 DSH Agent Worker；
- Worker 持续调用 `wb_list_agent_tasks` / `wb_claim_agent_task`；
- 领取后周期性提交进度；
- 成功、失败、等待用户确认都必须落库；
- 页面显示当前是否有常驻执行器、执行器名称、最后心跳和异常原因；
- 不能只提示用户输入“处理页面 AI 任务”这种不明确文字。

### 3. 项目与会话绑定不清晰

标识定义：

| 标识 | 含义 |
|---|---|
| `sessionId` | 当前 DSH 对话 |
| `assistantKey` | 稳定助手身份 |
| `workspaceId` | 长期工作区 |
| `projectId` | 具体项目 |

要求：

- 从 DSH 调用 `wb_open_workbench` 时必须携带上述上下文；
- 页面按钮请求必须沿用打开页面的 `sessionId`；
- 新 DSH 会话绑定同一助手和同一项目时，继承原 design/write/review 阶段；
- 切换到其他项目时从 design 开始，防止阶段污染；
- 直接打开 localhost 时必须明确提示这是独立本地会话，不要假称已绑定 DSH。


### 7. 文献检索质量差

目标流程：

```text
用户检索意图
→ DSH 理解和拆解查询
→ 提供中文、英文、同义词、领域词、年份约束
→ Core 调用 OpenAlex/Crossref 等多源，需要补充IEEE,arx.，谷歌学术等多数据库的多源搜索
→ 去重
→ 相关性重排和可信度评分
→ 检索事件回传 DSH
→ 工作台卡片展示
→ 用户确认后加入书目或绑定证据
```

要求：

- DSH 负责理解意图，不要只把整句原样传给供应商；
- Core 支持中文 query、英文 query、同义词、领域词、年份范围；
- 至少支持谷歌学术；
- 按标题、摘要、作者、来源、年份、元数据完整度、引用量综合评分；
- 自动 DOI/标题去重；
- 卡片显示标题、作者、年份、来源、DOI、引用量、相关性分数、命中词和数据源；
- 明确区分候选文献、已确认书目、全文材料和正文证据；
- 加入书目必须有确认；重复加入要明确提示；
- 书目在工作台“引用/来源”页面可查看；
- 检索请求、供应商响应、去重数量、排序结果写入协作事件；
- 不能把引用量当作相关性的唯一依据。

### 8. 正文、行文逻辑和审查意见编辑

要求：

- 大纲节点可编辑；
- 行文逻辑块可编辑：写作目的、核心论点、前后过渡、证据要求、风格约束；
- 正文可分块编辑，避免整篇覆盖；
- 保存必须进行 revision 校验；
- 审查意见可编辑为用户版本，但不能自动改写正文。

### 9. 统一 Diff 和用户确认

AI 生成结果必须形成 ChangeSet，覆盖：

- 大纲 Diff；
- 行文逻辑 Diff；
- 正文 Diff；
- 审查意见 Diff；
- 证据来源和生成理由。

要求：

- AI 只提交候选，不直接写入；
- 每项变更可单独勾选；
- 用户确认后才应用；
- 空选择表示拒绝；
- ChangeSet 有 `baseRevision`，过期时拒绝应用；
- 页面显示变更前、变更后、来源、理由和关联任务；
- 应用、拒绝、冲突都写入审计和协作事件。

### 10. SQLite-only 架构

要求：

- `.db` 运行时 SQLite 是唯一主存储；
- 不再持续写入 `workbench_state.state_json`；
- 旧 `state.json` 或旧快照只允许首次启动导入一次；
- 重启后从 SQLite 恢复项目、工作区、绑定、阶段、材料、文献、任务、ChangeSet 和审计；
- 不得要求用户删除数据库来“修复”升级；
- 数据迁移必须可重复执行且不会重复导入。

## 三、运行和重开要求

### 从 DSH 打开

DSH 调用 `wb_open_workbench`，Core：

1. 检查本地 Core 健康状态；
2. 复用已有服务或启动新服务；
3. 返回包含会话和项目上下文的 localhost URL；
4. 页面与 DSH 共享同一 SQLite 和协作事件流。

### 手动打开

```powershell
cd D:\雷达毕设相关\high_star\workbench-core
npm.cmd run start:workbench
```

健康检查：

```powershell
Invoke-RestMethod http://127.0.0.1:3200/health
```

重启 Core 或 DSH 不得丢失项目数据。代码更新通常需要重启 Core 和 DSH 会话，不应要求重装；只有插件不是本地链接或依赖变化时才需要重新注册/安装。

## 六、本次完成记录（2026-09-13）

- 已增加持久化 `agent_workers`，并提供注册、心跳、停止、状态查询及页面在线/过期状态展示。未配置真实执行器时，任务明确显示为等待领取；系统不会伪造 AI 执行进度。
- 已增加 `GET /api/collaboration-events/stream`（SSE），刷新或重连可按 `after` 时间戳补取协作事件。
- 文献检索页面现在可选择 OpenAlex、Crossref 与 Google Scholar 数据源、年份范围；Google Scholar 通过已授权的 SerpApi 适配器提供，需管理员设置 `SERPAPI_API_KEY`，未配置时会显示明确的数据源错误而不会降级伪造结果。
- 验证记录：`npm.cmd run check`、`npm.cmd test` 全部通过；`npm.cmd run start:workbench` 后 `/health` 返回 `status: "ready"`、`storage: "sqlite"`。

### DSH 对话注入补充（2026-09-13）

- 已接入当前 DSH `AgentRegistry`：页面创建任务后，Core 以原始 `sessionId` 查找 live Agent，并调用 `agent.followup()` 写入可见的“工作台请求 #任务号”消息，同时唤醒该会话的下一轮 Agent 执行。
- 注入消息携带项目、任务类型和安全处理约束；Agent 必须先领取任务，且只能提交候选、进度、结果或失败，不能绕过 ChangeSet/用户确认。
- 不存在 live Agent 时，系统写入 `chat_injection_unavailable` 协作事件及具体原因；成功时写入 `chat_injected`。两种情况均可由页面 SSE 或事件列表读取，绝不伪造送达。
- 已新增端到端测试，验证页面任务的注入回执和协作事件写入；需重启 DSH 使本地链接的插件代码重新加载。

### 旧任务恢复与交互修复（2026-09-13）

- 已定位旧 `queued` 任务会滞留的根因：它们可能由独立 localhost 页面创建并绑定到 `default` 会话，且手动启动的 Core 不拥有 DSH live Agent 注入器。
- 队列中的 `queued` 卡片新增“发送到当前 DSH 对话”按钮；它会使用当前页面的 `sessionId` 重新派发，成功/失败均落协作事件。DSH 同时提供 `wb_dispatch_queued_agent_task`。
- 仍需从 DSH 调用 `wb_open_workbench` 打开页面，并重启 DSH 后生效；独立手动启动页面始终如实标为本地会话，不能自动唤醒 DSH。
